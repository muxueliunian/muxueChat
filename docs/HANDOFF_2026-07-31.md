### 1.2 新增能力

**上下文压缩**（`domain/context/`）

## 2. 已知未验证的风险（bug 最可能出在这里）

按可疑程度排序：

1. **v8 迁移的数据搬迁**。`conversation_rp_settings` 整表重建，schema 对得上，
   但老数据是否完好**没有自动化测试**（Room migration test 是 instrumented test，
   本地跑不了）。症状会是：升级后老会话的角色卡/世界观绑定丢失，或启动崩溃。
   排查：Logcat 搜 `Migration` / `IllegalStateException`。

2. **tool_calls 流式分片的真实格式**。`DeepSeekToolCallAccumulator` 按文档描述实现，
   单测覆盖逻辑但**没跑过真实响应**。症状：建卡时提示「模型返回的参数不是合法 JSON」。
   排查：Logcat 搜 `muxueChat.ChatRepository`，看 `Settings tool parse failed`。

3. **thinking 语义**。改成显式发 `disabled` 后没有真机验证。
   `ChatRepositoryImpl.toUserFacingMessage()` 里保留了
   `"thinking options type cannot be disabled"` 的错误映射作为兜底——
   **如果这条提示真的出现了，说明服务端不接受显式 disabled，需要重新核实文档。**

4. **流式 + 工具的终止判断**。`generateAssistant` 里改成
   `if (!receivedTerminalEvent && !accumulator.hasCalls()) error(...)`。
   如果 DeepSeek 在纯工具调用时的 finish_reason 行为与预期不同，
   可能出现「流式响应提前结束」误报。

5. **自动压缩的时机**。放在发请求之前，跨过阈值那一轮会多等一次摘要请求，
   用户可能感觉「偶尔某一轮特别慢」。这是设计取舍，不是 bug，但值得确认用户能否接受。

6. **`ContextWindowSheet` 只在打开时刷新一次**（`refreshContextWindow()`），
   顶栏的百分比在没打开过面板时是 null，不会显示红色警示。

## 3. 明确没做完的部分

- **文风没有手动创建/编辑入口**，目前只能由 AI 工具生成。
  数据层、Repository、prompt 注入、迁移都已就绪，缺的是 UI。
- **RP 设置面板里不能选择绑定哪个文风**。`RpSettingsSheet` 未改。
- **UI 整体视觉没动**，只加了必要的新组件。用户说装上之后再针对性调。
- **附件内容会存进 Room**（作为用户消息的一部分）。这偏离了原任务书
  「原始文档不入库」的要求，是有意的取舍——不存的话历史会不连贯。
  用户尚未表态，如果要改成「只在请求时注入、消息里只留文件名」需要另做。

## 4. 关键设计决策（不要随意推翻）

- **硬裁剪不可关闭**，是防请求超长的最后保险；压缩才是可选项。
- **压缩目标线强制低于触发线至少 10 个百分点**，否则压完立刻又达标，每轮都发摘要请求。
- **最近 4 条消息永远逐字保留**（`MIN_MESSAGES_TO_KEEP_VERBATIM`）。
- **保留窗口必须以 user 消息开头**，否则模型看到没有对应输入的回复。
- **工具结果消息不回传草稿全文**，只给 id 和状态，否则上下文里存两遍。
- **草稿只在内存**，进程被杀就丢失，这是可接受的——存 Room 反而要写清理逻辑。
- **摘要请求失败不写任何状态**，下次重试，绝不留半截摘要。
